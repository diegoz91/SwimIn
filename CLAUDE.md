# SwimWaveUp (SwimIn) — Guida per Claude

Social network professionale per il mondo del nuoto, ispirato a LinkedIn.
Utenti: **professionisti** (istruttori FIN, assistenti bagnanti, allenatori, direttori sportivi) e **strutture** (piscine, centri sportivi).

## Stack
- React 19 + TypeScript (strict) + Vite 6, React Router 6, Tailwind 3.4
- Backend BaaS: **Appwrite Cloud** (Auth, Databases, Storage, Realtime) — SDK web `appwrite`
- Deploy: Vercel (SPA rewrite in `vercel.json`)
- Alias import: `@/` → `src/`

## Comandi
- `npm run dev` — dev server su porta 3000
- `npm run build` — `tsc && vite build` (deve passare prima di ogni commit)
- `npm run typecheck` — solo controllo dei tipi
- `npm test` — test del frontend (Vitest, file `src/**/*.test.ts`)
- `npm run setup-db` — crea/aggiorna DB, collezioni, indici, bucket e deploya la Function `api` (richiede `.env.setup` con API key, MAI committarlo)
- `npm run reset-db -- --yes` — ⚠️ cancella tutto l'ambiente di test
- `cd functions/api && npm test` — test della Function server-side
- Guida operativa: `docs/SETUP-APPWRITE.md`

## Variabili d'ambiente
- `.env` (frontend): `VITE_APPWRITE_ENDPOINT`, `VITE_APPWRITE_PROJECT_ID`
- `.env.setup` (script Node): `APPWRITE_ENDPOINT`, `APPWRITE_PROJECT_ID`, `APPWRITE_API_KEY`
- Entrambi sono in `.gitignore`. Non scrivere mai chiavi nel codice.

## Struttura
- `src/pages/` — pagine di route (Landing per i visitatori su `/`, Home, Jobs, Network, Profile, Chat, Live, PostPage `/post/:id`, Notifications `/notifiche`, Search `/cerca`, PublicJob `/offerte/:id`, Saved `/salvati`, Groups `/gruppi` e GroupPage `/gruppi/:id`, Events `/eventi` ed EventPage `/eventi/:id`, Onboarding `/benvenuto`, Login, Register, ResetPassword, VerifyEmail, NotFound) e `src/pages/legal/` (privacy, termini, cookie). Tutte caricate con `React.lazy` in `App.tsx`
- `src/features/<dominio>/components/` — UI per dominio: auth, feed, jobs, network, messaging, profile
- `src/services/database.ts` — **unico punto di accesso** alle collezioni Appwrite; i componenti non devono chiamare `databases.*` direttamente
- `src/services/storage.ts` — upload di immagini (compresse con `utils/image.ts`) e video; `deleteByUrl` per pulire i file sostituiti
- `src/config/legal.ts` — dati del titolare per le pagine legali (**da completare prima del lancio**)
- `src/hooks/useAuth.tsx` — sessione e profilo utente corrente
- `src/types/types.ts` — tipi di dominio; tenerli allineati allo schema in `setup-db.js`
- `setup-db.js` — **fonte di verità dello schema** Appwrite (tabelle, colonne, indici, permessi). Usa l'API **TablesDB** (Appwrite 1.8+); la vecchia API Databases per schema/collezioni è deprecata e la console non offre più i suoi scope
- `functions/api/` — Appwrite Function per le operazioni che toccano dati di più utenti; il client la chiama con `callApi()` in `database.ts`
- `api/` — funzioni Vercel: `/u/:id` (anteprime social del profilo pubblico), `/sitemap.xml`, `/robots.txt`. Chiamano solo le azioni pubbliche della Function (`PUBLIC_ACTIONS` in `functions/api/src/public.js`), senza chiavi segrete; test in `scripts/vercel/api.test.mjs`
- `.github/workflows/deploy-appwrite.yml` — su main lancia `setup-db` (schema + Function) se ci sono i secret `APPWRITE_*`; senza, va lanciato a mano dopo ogni merge che tocca `functions/api/` o `setup-db.js`
- `.github/workflows/ci.yml` — CI su ogni PR: sincronizza `package-lock.json`, type-check, build, test della Function

## Design system (SwimIn, "acqua premium")
- Colori (token Tailwind in `tailwind.config.js`): `abisso` #0A2738 testi forti, `corsia-*` azioni (la scala `blue-*` è ricalibrata sullo stesso blu), `cloro-*` accenti, `piastrella` #F2F8FA sfondo, `galleggiante` #E23D3D **solo** SOS ed errori (per i testi `text-galleggiante-700`, per il contrasto), `oro-*` **solo** SwimIn Premium (badge `<PremiumBadge />`, pagina `/premium`).
- Tema chiaro e scuro: ogni colore Tailwind è una variabile CSS (plugin in `tailwind.config.js`), con la classe `dark` su `<html>` tutto passa al tema scuro. Regole: `bg-white` è la superficie delle schede (scura nel tema scuro), `text-white` resta bianco (testo su pulsanti colorati); grigi `slate-*` si capovolgono; tinte chiare (50-300) diventano tinte scure come sfondi e bordi; per i testi le tonalità 600-950 diventano chiare. Niente colori esadecimali nei componenti: se servono in SVG o grafici usare `rgb(var(--c-…))` / `rgb(var(--t-…))`. Scelta del tema in `utils/theme.ts` (localStorage, applicata da `index.html` prima del disegno), `useTheme`, `ThemeSegmented` nel menu dell'avatar e `ThemeCards` in Impostazioni › Aspetto. Le schermate CI includono `*-scuro-*` con controllo di layout e accessibilità.
- Barre di scorrimento nascoste in tutta l'app (`globals.css`): lo scorrimento resta con rotella, dita e tastiera.
- Font: Figtree (testo) e Barlow Condensed (`font-display`, applicato a h1/h2), ospitati con l'app via @fontsource. Niente Google Fonts o CDN esterni.
- Elemento distintivo: la corsia. Logo = `<Brand />`/`<BrandMark />` (T di fine corsia), classe `.lane-rope` per il galleggiante. Usarlo con parsimonia (header, landing, live).
- Avatar: `avatarOf()` / `displayNameOf()` / `headlineOf()` in `utils/profile.ts`; mai servizi esterni per le iniziali.
- Testi in sentence case, niente maiuscolo per etichette o pulsanti, niente emoji decorative nei controlli.
- Conferme: mai `window.confirm`, `alert` o `prompt` (finestre del browser). Usare `useConfirm()` da `context/ConfirmContext.tsx` (`if (!(await confirm({ title, message, confirmLabel, tone: 'danger' }))) return;`), avvisi con `showToast`. Un test end-to-end fallisce se compare una finestra del browser.
- Controlli: mai `<select>`, `type="date"`, `type="time"`, `datalist` o checkbox nativi. Usare `Select`, `DatePicker` (gg/mm/aaaa, valore ISO), `TimePicker` (24 h), `MonthYearPicker`, `SuggestInput`, `CityCombobox` da `components/form/Pickers.tsx`, `Checkbox` da `Field.tsx`, e `LocationFields` per la coppia provincia/comune. Si aprono in un portale (non vengono tagliati dalle modali) e su mobile come foglio dal basso.
- Anagrafica: province in `src/data/generated/province.json`, comuni in `public/data/comuni/<SIGLA>.json`, generati da `scripts/anagrafica/update.mjs` dalla fonte ISTAT (workflow mensile `Anagrafica comuni`, che apre una PR). Non modificarli a mano. Il comune va validato con `comuneOf()` e `useComuniSync()`.
- Form: usare `useForm` (`hooks/useForm.ts`) con regole da `utils/validation.ts`, campi `Field` / `ProvinceSelect` / `MonthYearPicker` da `components/form/` e la modale `FormModal` (foglio dal basso su mobile, conferma se ci sono modifiche). Date di calendario come stringhe ISO (`YYYY-MM-DD`, mesi `YYYY-MM`) con gli helper di `utils/dates.ts`; mai date in testo libero. Elenchi del settore (ruoli, brevetti, enti, servizi) in `data/swimming.ts`, province in `data/italy.ts`.
- Revisione visiva: il workflow `Schermate` pubblica le schermate (dati di esempio in `scripts/screenshots/fixtures.mjs`) sul branch `ci-screenshots/<branch>`; per vederle `git clone -b ci-screenshots/<branch> …`. Formati: desktop 1440, laptop 1280, tablet 820 e 1180 (orizzontale), mobile 390, mobile piccolo 360. Ogni schermata passa un controllo del layout (`layout.md` sul branch): la CI fallisce se una pagina scorre in orizzontale o un elemento esce dallo schermo; segnala anche i controlli touch sotto 24×24 px (WCAG 2.5.8).
- Qualità in CI (stesso workflow `Schermate`, rapporti sul branch `ci-screenshots/<branch>`): accessibilità axe-core WCAG 2.1 A/AA su computer e smartphone (`a11y.md`, la CI fallisce con problemi gravi o critici: contrasto almeno 4,5:1, nome accessibile per link e pulsanti di sola icona, niente controlli annidati; i duplicati decorativi come l'avatar accanto al nome vanno con `tabIndex={-1} aria-hidden="true"`); test end-to-end dei percorsi principali in `scripts/e2e/flows.mjs` (`e2e.md`); LCP/CLS della landing su smartphone lento e budget del bundle gzip in `scripts/quality/bundle-budget.mjs` (`perf.md`). L'Appwrite finto condiviso è `scripts/screenshots/mock.mjs`. I grigi `slate-400`/`slate-500` sono ricalibrati in `tailwind.config.js` per il contrasto.
- Guscio dell'app (utenti con accesso): intestazione in alto e menu in basso fermi, scorre solo il contenuto in mezzo (`#scroll-root` in `App.tsx`, altezza `100dvh`). Per scorrere la pagina da codice usare `scrollPageTo()` (`utils/scroll.ts`), non `window.scrollTo`; gli elementi `sticky` hanno offset piccoli (`top-4`/`top-6`) perché l'intestazione non copre più il contenuto. Un test end-to-end controlla che le due barre restino ferme. In fondo al contenuto c'è il piè di pagina dell'app (`components/layout/AppFooter.tsx`: scopri, account, legale): i link legali stanno lì, non nelle colonne laterali.
- Responsive: niente testi troncati (`truncate`) dentro elementi di griglia o flex senza `min-w-0` sul contenitore (allargano la colonna e la pagina); link e pulsanti di solo testo con area di tocco ampliata (`py-1 -my-1`); etichette nascoste su mobile con `sr-only sm:not-sr-only`, non `hidden`; il widget dei messaggi compare da `xl`, la ricerca nell'intestazione da `lg`.

## Convenzioni
- UI, testi e messaggi d'errore in **italiano**; nomi di variabili/funzioni in inglese.
- Ogni nuovo campo di un documento va aggiunto sia in `setup-db.js` sia in `types.ts`.
- Niente `as any` nuovi; non silenziare errori con `catch {}` vuoti: logga o mostra un toast (`ToastContext`).
- Componenti funzionali + hooks, Tailwind per lo stile.

## Sicurezza (priorità)
- I permessi vanno impostati **per documento** (document security), non `update/delete(Role.users())` a livello di collezione.
- Passano dalla Function `api` (che verifica l'utente tramite `x-appwrite-user-id`) le operazioni che toccano dati di altri utenti **o** che devono garantire l'identità dell'autore: creazione di post e annunci, collegamenti, like, commenti, conferme di competenze, candidature, assunzioni, follow, notifiche, messaggi, segnalazioni, eliminazione account. Nuove azioni del genere vanno aggiunte lì, con un test in `functions/api/test`.
- Mai fidarsi di campi "chi sono" inviati dal client (`authorId`, `structureId`, elenchi `connections` del chiamante): un utente può modificare il proprio profilo, quindi i controlli devono usare dati che solo il server o l'altra parte possono scrivere.
- I messaggi privati devono essere leggibili solo da mittente e destinatario. Allegati (`functions/api/src/chat.js`): il client li carica nel bucket privato `chat_files` leggibili solo da sé (`services/chatFiles.ts`), la Function verifica che il file sia del mittente e aggiunge la lettura per il destinatario; il client li mostra scaricandoli con un JWT (`chatFileUrl`). Risposte (`replyPreview`), reazioni (`reactMessage`) ed eliminazione per tutti (`deleteMessage`, solo il mittente) passano dalla Function.
- Righe create dalla Function: **solo permessi di lettura** (mai `update`/`delete` per l'autore), altrimenti il client può riscrivere campi come `authorId`, `structureId`, `featured`, contatori. Modifiche ed eliminazioni passano da azioni dedicate (`deleteComment`, `closeJob`/`reopenJob`, `withdrawApplication`…). Eccezioni volute: notifiche (il destinatario le segna come lette) e salvati (`saves`, solo propri). `setup-db` toglie i permessi di scrittura rimasti sulle righe vecchie (`stripClientWrites`).
- Niente dati riservati sulle righe pubbliche: il profilo è leggibile da tutti, quindi "sta scrivendo" sta nella tabella `typing` (una riga per persona, leggibile solo dal destinatario; nel client `useTypingUsers`) e il link degli eventi online in `event_private` (restituito da `getEventLink` solo a organizzatore e iscritti).
- Limiti anti-spam nella Function (`rateLimit`, conta le righe recenti dell'utente): messaggi 30/min, commenti 20/min, post 15/ora, richieste di collegamento 100/giorno, segnalazioni 30/ora, chat staff 20/min. Risposta 429 con messaggio in italiano.
- Profili si modificano solo via Function (`updateMyProfile` in `functions/api/src/profile.js`): la tabella è in sola lettura per i client.
- Strutture: **un solo modello**, l'account Struttura (`userType: 'structure'`, scelto all'iscrizione). Niente pagine struttura create dalle persone (tabella `facilities` e azioni `createFacility`/`updateFacility`/`toggleFollowFacility` rimosse). Per gestire la struttura in più persone il titolare sceglie dallo staff fino a 5 **co-amministratori** (`coAdmins` sul profilo, `setCoAdmin` in `team.js`, UI in `TeamMembers`): gestiscono annunci e candidati (`jobManagers`, `createJob` con `structureId` della struttura), staff, turni e bacheca e rispondono alle recensioni; il profilo della struttura, le statistiche e i co-amministratori li gestisce solo il titolare. Un co-amministratore che esce dallo staff perde il ruolo. Nel client `useManagedStructures()` (account Struttura o `useMyTeams()` con `role: 'admin'`).
- Amministratori: utenti con l'etichetta `admin` (Console Appwrite → Auth → utente → Labels). Le azioni `admin*` della Function lo verificano sempre; il client usa `useBlocks().isAdmin` solo per mostrare il pannello `/admin`.
- Area staff di una struttura (bacheca, chat staff, turni, membri): solo amministratori (titolare e co-amministratori) e membri di `staff` della struttura, verificati dalla Function a ogni lettura (`functions/api/src/team.js`). Un collegamento o un follower **non** è staff. Le tabelle `announcements`, `shifts`, `staff_messages` e `staff_chat_reads` non hanno permessi per i client. La chat staff (`listStaffMessages`, `sendStaffMessage`, `deleteStaffMessage`; UI in `features/team/StaffChat.tsx`) si aggiorna a intervalli mentre è aperta, perché senza permessi non c'è Realtime; le notifiche push hanno tipo `staff_chat` e portano a `/profile/:id?area=chat-staff`.
- Dati privati: email solo nell'account (mai sul profilo); telefono delle persone in `private_info`, restituito da `getContactInfo` solo alla persona, ai collegamenti reciproci e a chi valuta una sua candidatura.
- Post, eventi e dirette si modificano/annullano solo via Function (`updatePost`, `createSwimMeet`, `updateSwimMeet`, `cancelSwimMeet`, `endLiveRoom`).
- Eventi (`functions/api/src/events.js`, tabella `swim_meets`): tipi in `data/events.ts` ed `EVENT_TYPES` lato server, online con link, quota, posti con lista d'attesa (`waitlist`: chi rinuncia libera il posto al primo in attesa, avvisato con una notifica `event`), eventi di un gruppo (`groupId`, solo membri se il gruppo è su approvazione). Il calendario si scarica con `downloadEventIcs` (riusa `utils/ics.ts`).
- Lavoro: bacheca `/jobs`, annuncio `/jobs/:id` (`JobPage`: dettagli e candidatura; per chi lo gestisce anche i candidati in `CandidatesPanel`), `/jobs/candidature` (percorso a tappe di ogni candidatura) e `/jobs/annunci` (`MyJobs`, gestionale annunci della struttura e dei suoi co-amministratori; `?struttura=`). I link vecchi `/jobs?annuncio=` reindirizzano. Fasi delle candidature e testi in `features/jobs/applicationStatus.ts` (pending = nuova, reviewed = vista, aprendola senza notifica; accepted = selezionata, notifica `application_update`; hired con `hireCandidate`; rejected). Modifica degli annunci con `updateJob` (gli SOS solo descrizione e compenso), elenco con conteggi per fase con `listStructureJobs`. Candidature e flusso condivisi in `useApplyFlow`; strutture gestite in `useManagedStructures`.
- Selezione e colloqui (`functions/api/src/interviews.js`): valutazione a stelle e nota **interne** (`getApplicationReviews`/`saveApplicationReview`, tabella `application_reviews` senza permessi per i client, una riga per candidatura, mai visibili al candidato); proposta di colloquio (`proposeInterview`: data, ora, modalità presenza/video/telefono, luogo o link https) salvata sulla candidatura (`interview*`), il candidato conferma o chiede un altro orario (`respondInterview`). UI in `features/jobs/components/Interview.tsx` (`InterviewModal`, `InterviewCard` con `AddToCalendar`, `StarRating`) e `CandidatesPanel`.
- Offerte pubbliche (`/offerte/:id`, pagina `PublicJob`): la funzione Vercel `api/job.js` aggiunge meta tag e dati strutturati schema.org `JobPosting` (Google Jobs); i dati vengono da `publicJob`/`publicJobs` (azioni pubbliche: niente candidati né dati interni) e le offerte aperte sono nella sitemap. Chi si iscrive da un'offerta ci torna dopo il benvenuto (`utils/pendingJob.ts`).
- Referenze scritte (`functions/api/src/recommendations.js`, tabella `recommendations`): le scrivono collegamenti reciproci, la struttura per lo staff o chi ha valutato una candidatura; restano `pending` (leggibili solo da autore e destinatario) finché il destinatario non le pubblica (`published`, leggibili da tutti) o le nasconde. I permessi della riga cambiano con lo stato (`update` con `permissions`). UI in `features/profile/components/RecommendationsSection.tsx`; richiesta dal menu del profilo.
- Ricerca (`/cerca`): persone, strutture, offerte, gruppi, eventi, post e hashtag (`searchGroups`, `searchEvents`, `searchHashtags` in `database.ts`).
- Avvisi di lavoro (`functions/api/src/alerts.js`, tabella `job_alerts` leggibile solo dal proprietario): parole chiave, provincia, contratto, solo SOS; al massimo 10 per persona. `createJob` chiama `_notifyJobAlerts` (notifica `job_alert`, una per persona, massimo 500 per annuncio). UI in `features/jobs/components/JobAlertsModal.tsx`.
- Profili pubblici (`/u/:id`): strutture sempre, persone solo con `publicProfile` attivo. La Function è eseguibile anche dagli ospiti, ma senza login accetta solo `PUBLIC_ACTIONS`, che restituiscono dati non sensibili.
- Interazioni social (`functions/api/src/social.js`): reazioni ai post (`react`, tipi in `data/reactions.ts` e `REACTIONS` lato server), mi piace ai commenti, ripubblicazioni (`repost`/`undoRepost`, sempre dell'originale) e visite al profilo (`recordProfileView`, notifica al massimo una volta ogni 24 ore per visitatore, anonima con `hideProfileViews`; la tabella `profile_views` la legge solo la Function).
- SwimIn Premium (`functions/api/src/billing.js`): il diritto è `premiumUntil` sul profilo, scritto solo dalla Function (prova, webhook Stripe/PayPal firmati su `/webhooks/*`, omaggi admin). Tre piani (`audienceOf`): professionisti, appassionati (Premium Passione) e strutture. I vantaggi si verificano lato server (`isPremium`): messaggi diretti a non collegati (`checkMessagingAllowed`, crediti mensili `INMAIL_CREDITS`), annunci attivi (`BASE_ACTIVE_JOBS` = 2) e in evidenza, area staff (`BASE_STAFF` = 5 in `hireCandidate`), avvisi di lavoro (`BASE_ALERTS` = 2), SOS anche nelle province della stessa regione (`regions.js`, dati in `functions/api/src/data/regioni.json` generati dall'anagrafica), candidature in cima (`priority` sulla candidatura), precedenza nelle liste d'attesa degli eventi, visite e statistiche, visite anonime solo verso profili Base. Il confronto mostrato all'utente è `PLAN_FEATURES` in `utils/premium.ts`: tenerlo allineato. Prezzi: predefiniti in `PRICES`, modificabili dagli amministratori in *Admin › Piani e prezzi* (`adminGetPlans`/`adminUpdatePlans`, tabella `plans` senza permessi per i client); i nuovi prezzi Stripe e piani PayPal si creano a runtime (`ensureStripePrice`/`ensurePaypalPlan`), gli abbonati esistenti mantengono il loro prezzo. Nel client `isPremium()` in `utils/premium.ts` serve solo alla UI; un errore con `code: 'premium_required'` apre da solo l'invito (`requestPremium`).
- Verifica in due passaggi (TOTP di Appwrite, `services/mfa.ts`, UI in `features/profile/components/TwoFactorSetup.tsx`): app di autenticazione + codici di recupero; al login `useAuth().login` restituisce `'mfa'` e `completeMfa` chiude la sfida.
- Filtro testi (`functions/api/src/textfilter.js`): `assertClean(text, kind)` su post, commenti, messaggi in diretta, gruppi, eventi, referenze e recensioni; blocca insulti (anche camuffati) e spam evidente con errore 400 `text_blocked`. Le parole ambigue vanno solo come parola intera; i falsi positivi si correggono in `BLOCKED`/`ALLOWED` con un test in `textfilter.test.js`. Post identici entro 10 minuti: 409.
- Feed "Per te" (`utils/feedRank.ts`): ordinamento nel client per collegamenti, seguiti, provincia, interazioni e freschezza; la scelta "Per te"/"Più recenti" resta nel browser.
- Riepilogo settimanale (`functions/api/src/digest.js`): esecuzione programmata della Function (`schedule` in `setup-db`, lunedì 6-18 UTC, 250 persone per volta, `digestSentAt` sul profilo). Solo email (categoria `digest` delle preferenze, attiva di default), niente email se non c'è nulla di nuovo; richiede `EMAIL_NOTIFICATIONS=on`.
- Contenuti (`functions/api/src/content.js`): hashtag e menzioni li estrae la Function dal testo (`hashtags`, `mentions` sul post; menzioni salvate come `@[Nome](id)`, nel client `MentionTextarea` + `toEditable`/`fromEditable` e `RichText` per mostrarle). Sondaggi (`votePoll`, voti in `poll_votes` leggibili solo da chi vota), segui (`toggleFollow`, tabella `follows` pubblica, contatori sul profilo).
- Gruppi (`functions/api/src/groups.js`): tabelle `groups` e `group_members` in sola lettura per i client, scritte solo dalla Function (`createGroup`, `joinGroup`, `moderateMember`…). Gli amministratori sono `admins` sul gruppo; pubblica nel gruppo (`createPost` con `groupId`) solo un membro `active`, e gli amministratori possono rimuovere i post. I post con `groupId` restano fuori dal feed principale (`Query.isNull('groupId')`). Sui post di un gruppo commentano solo i membri; gli amministratori del gruppo possono eliminare post e commenti.
- Tempo reale (ogni azione si vede subito dagli altri, senza ricaricare): per le tabelle che il client può leggere (offerte, post, commenti, eventi, notifiche, messaggi) Realtime diretto con `useLiveCollection` (`hooks/useLiveCollection.ts`); per i dati che passano solo dalla Function (turni, bacheca e chat staff, candidature, inviti, gruppi, collegamenti, referenze) la Function scrive un **segnale** nella tabella `signals` (una riga per destinatario, leggibile solo da lui, nessun dato: solo `topic` e `kind`) e il client ricarica con `useSignal('team:<id>' | 'job:<id>' | 'event:<id>' | 'group:<id>' | 'network:*' | 'recs:<id>' | 'staffchat:<id>', …)`. Nuove azioni che cambiano dati visti da altri vanno aggiunte a `SIGNALS` in `functions/api/src/main.js` (test in `signals.test.js`); i segnali vecchi li pulisce l'esecuzione programmata. Nel feed i post nuovi non spostano la lettura: compare l'avviso "N nuovi post". Negli e2e `state.pushRealtime(collezione, tipo, riga)` simula un evento.
- Google (`services/google.ts`, guida in `docs/SETUP-APPWRITE.md` §11): accesso e iscrizione con `GoogleButton` (OAuth2 di Appwrite a token: `startGoogle` → `/accesso/google` (`GoogleCallback`) → `createSession`; `state` controllato contro sessionStorage, ritorno solo su percorsi interni). Account senza profilo = `useAuth().incompleteAccount` → `/completa-account`. Calendario: sempre `AddToCalendar` (Google Calendar diretto con il token dell'identità Google e il permesso `calendar.events`, altrimenti link precompilato; oppure file .ics), id evento fisso con `googleEventId`. Interruttori `VITE_GOOGLE_AUTH=off` e `VITE_GOOGLE_CALENDAR_API=off`. Negli e2e il mock simula il ritorno da Google.
- Lavoro nelle strutture: `useMyTeams()` (una richiesta condivisa, aggiornata con i segnali `team:*`) alimenta le scorciatoie "Lavori presso" (menu dell'avatar, `MyWorkplaces` in home: scheda a sinistra su computer, striscia sopra il feed su smartphone) e il calendario personale `/turni` (`MyShifts`: settimana o mese con `ShiftMonth`, un colore per struttura, filtro `?struttura=`, ore del periodo e turni sovrapposti; logica in `utils/shiftCalendar.ts` con test). - CV personale (`functions/api/src/resume.js`, bucket privato `resumes`, solo PDF fino a 5 MB): il client carica il file leggibile solo da sé (`services/resume.ts`), `setMyResume` lo verifica, lo rende di sola lettura e salva nome/dimensione in `private_info` (mai sul profilo). Azioni leggere e reversibili (togliere un salvato, chiudere un annuncio, lasciare un gruppo aperto) non chiedono conferma: toast con "Annulla" (`showToast(msg, tipo, { action })`). In home un solo avviso alla volta (assunzione prima dei brevetti). Notifiche raggruppate per giorno, swipe con `SwipeAction` (sempre anche un pulsante). Ricerche recenti in `utils/recentSearches.ts`.

- Affidabilità (`functions/api/src/ops.js`, guida in `docs/SETUP-APPWRITE.md` §12): registro unico degli errori in `client_errors` (`source` client/server, `fingerprint` per raggruppare; gli errori 500 della Function li registra l'entrypoint con `_recordError`), avviso agli admin (notifica `system_alert`, webhook `ALERT_WEBHOOK_URL`) una volta l'ora per impronta; UI `features/admin/AdminErrors.tsx`. Stato del servizio nella riga `main` di `app_status` (leggibile da tutti, scritta con `adminSetAppStatus`): `useAppStatus()` (`AppStatusProvider`), `MaintenanceScreen`/`OutageScreen`/`StatusBanner` in `components/common/ServiceStatus.tsx` (restano aperti `MAINTENANCE_OPEN_PATHS`), pagina pubblica `/stato`, pannello `AdminStatus`, ripiego `VITE_MAINTENANCE=on`. `/api/health` su Vercel per i monitor; workflow `Monitor` (ogni 10 minuti, `scripts/ops/monitor.mjs`) e `Prova reale` (`scripts/real/flows.mjs`: account veri `swimin-e2e+…@example.com`, riconosciuti da `_isTestAccount`, eliminati alla fine). ## Workflow
- Branch per ogni intervento (`fix/...`, `feat/...`), commit piccoli, PR verso `main`.
- Prima di consegnare: CI verde sulla PR (in questa sessione il registry npm può non essere raggiungibile: la CI è il riferimento).
- Se modifichi `package.json`, la CI rigenera e committa il `package-lock.json`: fai `git pull --rebase` prima del push successivo.
- Gli errori di type-check si leggono dalle annotazioni del check-run (`gh api repos/.../check-runs/<job_id>/annotations`).
